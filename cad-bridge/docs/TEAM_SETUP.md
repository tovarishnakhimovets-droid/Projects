# Памятка: подключение машин и обновление CAD-моста

Одна инструкция для AutoCAD 2026/2027, Civil 3D 2027 и локального Codex.
Все команды выполняются в **Windows PowerShell**, по шагам, после успешного
завершения предыдущего. На другом компьютере меняются имя пользователя,
локальный путь к Projects и год AutoCAD.

Быстрый порядок:

- **Новая машина:** Git → исходники → доступ на push при необходимости → ZIP → установка → настройка Codex → проверка чтения.
- **Андрей:** сохранить правки → PR в develop → получить develop → собрать новый ZIP → установить → проверить → выложить на NAS.
- **Коллеги:** взять назначенный ZIP + SHA → закрыть CAD/Codex → установить локально → запустить и проверить чтение.

| Что | Где и зачем |
| --- | --- |
| GitHub / Git | Исходники и история изменений; общий принятый код в `develop` |
| Личная папка `Projects` | Своя копия исходников на каждом компьютере разработчика |
| NAS | Готовые версионные ZIP и их `.sha256`; точный общий путь сообщает ответственный |
| Локальная установка | DLL в ApplicationPlugins и EXE в server/current; с ней работает Codex |

**`git pull` обновляет исходники. `install.ps1` обновляет работающий мост.**
Codex запускает локальный сервер сам. Общий EXE на NAS не используется.
VS Code для работы готового моста открывать не требуется.

Пример версии ниже — **`2.0.1-team.4-rc.1`**, тестовый пакет исправления
автозагрузки. Для очередного обновления подставляй версию, которую назначил
ответственный. RC — кандидат для проверки, не стабильный выпуск. У `team.3`
подтверждён сбой автозагрузки: его новым сотрудникам не устанавливаем.
Актуальные проверки и готовность выпуска находятся в едином [WORK_STATUS.md](../WORK_STATUS.md).

## 1. Первая настройка новой машины

### 1.1. Установить программы

1. Установить Git for Windows с [официальной страницы](https://git-scm.com/install/windows).
2. Установить нужный AutoCAD или Civil 3D и проверить обычный запуск.
3. Установить локальный Codex и войти в свой рабочий аккаунт.

После установки Git открыть **новое** окно PowerShell и проверить:

```powershell
git --version
```

Git нужен для исходников и совместных доработок. Если сотрудник только работает
с готовыми CAD-инструментами, можно перейти сразу к пункту 1.4: для установки
ZIP Git, Python и .NET SDK не требуются.

### 1.2. Получить исходники

Путь ниже — наш принятый пример. Если диска D: нет, выбрать другой локальный
путь и подставлять его дальше. Папка Projects должна ещё не существовать;
повторно клонировать поверх уже имеющейся папки не нужно.

```powershell
New-Item -ItemType Directory -Path 'D:\CAD-Automation\team' -Force
Set-Location 'D:\CAD-Automation\team'
git clone --branch develop https://github.com/tovarishnakhimovets-droid/Projects.git Projects
Set-Location '.\Projects'
git status --short --branch
```

`New-Item` создаёт папку; `-ItemType Directory` означает каталог; `-Path` задаёт
его путь; `-Force` допускает уже существующий родительский каталог.
`Set-Location` переходит в папку. `clone` получает репозиторий один раз;
`--branch develop` сразу выбирает принятый командный код. `Projects` — имя
создаваемой папки. В `status` флаг `--short` даёт краткий список, `--branch`
показывает ветку. После клонирования ожидается `develop...origin/develop`
без списка изменённых файлов.

Публичный репозиторий можно читать по HTTPS без SSH. Если GitHub запросил
доступ к закрытому репозиторию, войти своим аккаунтом и получить доступ у владельца.
Правки ведём в `Projects/cad-bridge`; повторно скачивать upstream не требуется.
[Порядок клонирования GitHub](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository).

### 1.3. Настроить публикацию изменений — только разработчику

У каждого свой GitHub-аккаунт с доступом к репозиторию и свои имя/email автора.
Владелец добавляет сотрудника в доступы репозитория. Имя и почта в Git — подпись
коммитов, они сами по себе не дают права пушить.

```powershell
git config --global user.name 'Имя Фамилия'
git config --global user.email 'your-email@example.com'
```

Заменить значения своими. `--global` задаёт настройки пользователя этого компьютера.
Для SSH сначала проверить, нет ли уже ключа:

```powershell
Get-ChildItem -LiteralPath "$env:USERPROFILE\.ssh" -Filter '*.pub'
```

`-LiteralPath` — точный путь, `-Filter` — отбор файлов по имени. Если ключ уже
есть, использовать его; **не перезаписывать существующий ключ**. Если ключа нет:

```powershell
ssh-keygen -t ed25519 -C 'your-email@example.com'
Get-Content -LiteralPath "$env:USERPROFILE\.ssh\id_ed25519.pub"
```

`-t ed25519` выбирает тип ключа, `-C` добавляет подпись. При создании можно
принять стандартный путь Enter и задать пароль ключа. При таком пути SSH
обычно найдёт ключ сам; если запрашивается пароль ключа, ввести его.
Публичную строку из `.pub` добавить **в свой аккаунт GitHub**:
Settings → SSH and GPG keys → New SSH key. Приватный файл без `.pub` не пересылать.
[Официальная инструкция по ключам](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent).

Из папки Projects переключить подключение на SSH и проверить:

```powershell
git remote set-url origin git@github.com:tovarishnakhimovets-droid/Projects.git
ssh -T git@github.com
```

`remote set-url` меняет адрес того же репозитория, не создавая копию.
`-T` проверяет SSH-аутентификацию без открытия терминального сеанса GitHub.
При первом подключении сверить fingerprint с
[инструкцией GitHub](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/testing-your-ssh-connection),
затем ответить `yes`. Сообщение об успешной аутентификации — хороший результат;
код возврата 1 у этой проверки GitHub допустим. `Permission denied (publickey)`
означает, что сначала нужно разобраться с ключом/аккаунтом.

Наши постоянные рабочие ветки: **andrew — Андрей, artem — Артём**, `develop` —
общий принятый код. Новому разработчику заранее согласовать своё имя ветки.
Для первой новой ветки, например `ivan`, из чистой develop выполнить:

```powershell
git switch -c ivan
```

`-c` создаёт новую ветку и переходит в неё. `ivan` — пример, заменить согласованным
именем. Если личная ветка уже есть на GitHub, создавать её заново не нужно:
выполнить `git fetch origin`, затем `git switch имя-ветки`.

### 1.4. Получить и установить готовый ZIP

1. Скопировать **ZIP нужной версии и соседний `.sha256`** с NAS в локальную
   папку. Номер версии сообщает ответственный; Git clone не скачивает готовые ZIP.
2. Открыть PowerShell в этой папке. Проверить файл и распаковать:

```powershell
$version = '2.0.1-team.4-rc.1'
$zip = "DwgMcp.Setup-v$version-win-x64.zip"
Get-FileHash -LiteralPath $zip -Algorithm SHA256
Get-Content -LiteralPath "$zip.sha256"
```

`$version` — устанавливаемая версия, `$zip` — её имя файла.
`-Algorithm SHA256` выбирает алгоритм контрольной суммы. Две строки хеша должны
совпасть **без учёта регистра букв**: это подтверждает, что ZIP скопирован без изменений. При несовпадении
остановиться и скопировать пакет заново.

Если ZIP отмечен как скачанный, разблокировать его через свойства файла либо:

```powershell
Unblock-File -LiteralPath $zip
```

Затем извлечь весь пакет в новую локальную папку:

```powershell
Expand-Archive -LiteralPath $zip -DestinationPath ".\DwgMcp.Setup-v$version-win-x64"
Set-Location ".\DwgMcp.Setup-v$version-win-x64"
```

`-DestinationPath` — папка распаковки. Не запускать установку из окна архива
и не распаковывать разные версии друг поверх друга.

3. Сохранить свою работу и **полностью закрыть AutoCAD/Civil 3D и Codex**.
   Из распакованной папки выполнить:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -Years 2027 -Client none
```

Для AutoCAD 2026 заменить `2027` на `2026`. Civil 3D 2027 использует вариант 2027.
`-NoProfile` — без профиля PowerShell; `-ExecutionPolicy Bypass` разрешает скрипт
только в этом процессе; `-File` — запускаемый файл; `-Years` — год плагина;
`-Client none` — подключение Codex настраивается отдельно следующим шагом.
Дополнительный `-WhatIf` показывает план без установки.

Ожидается версия нужного пакета, `Verified: Acad2027 match the package` и
`Server ... (check: OK)`. Сообщение `In use ... rollback ...` означает, что
остался работающий клиент/сервер: полностью перезапустить MCP-клиенты, чтобы
они использовали новую установку. Эти файлы установщик убирает при следующем
обновлении; вручную удалять работающие файлы не требуется.

### 1.5. Один раз настроить подключение Codex

Если на машине есть исходники из пункта 1.2:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\setup-codex.ps1 -AcadYear 2027 -BridgeSourceRoot 'D:\CAD-Automation\team\Projects\cad-bridge'
```

`-AcadYear` задаёт год MCP; `-BridgeSourceRoot` указывает **реальную локальную**
папку исходников, чтобы чат знал, где развивать мост. Для 2026 заменить год.
Если исходники не клонировались, выполнить ту же команду **без**
`-BridgeSourceRoot` и следующего за ним пути: готовый мост будет работать,
но для доработок сначала потребуется получить исходники.

Если скрипт пишет `Codex CLI is not in PATH`, установка моста не отменяется.
Скрипт выводит готовый TOML: в указанном им `config.toml` добавить или заменить
**только** блок `mcp_servers.dwg-2027` и его `.env`. Не создавать второй блок с тем
же именем и не затирать остальные MCP. Глобальное подключение хранится у
пользователя в `.codex/config.toml`; свой `CODEX_HOME` может менять этот путь.
[Официальная документация MCP в Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

### 1.6. Проверить первую автозагрузку

1. Запустить AutoCAD/Civil 3D обычным ярлыком, **без NETLOAD**.
2. Создать пустой чертёж или открыть нужный DWG. Исправленный автозапуск ждёт
   готового документа; одной стартовой вкладки для связи недостаточно.
3. Запустить Codex и попросить:

> Проверь dwg-2027: получи сведения об активном чертеже. Ничего не изменяй и не сохраняй.

Для 2026 в запросе использовать `dwg-2026`. Успех — ответ `ok=true` с нужным
документом. Если версия поддерживает нужный профиль, ожидается 58 инструментов;
в read-only — 20. Количество инструментов не доказывает работу каждой операции.

Сервер запускается Codex автоматически при подключении MCP; отдельное окно
с EXE каждый день открывать не нужно. Входить заново в Git после перезагрузки
для работы установленного моста тоже не требуется.

## 2. Обновление сервера у Андрея

**Если готовый проверенный ZIP уже получен — сразу пункт 2.3.**
Пункты 2.1–2.2 нужны, когда требуется принять доработки и выпустить новый пакет.

### 2.1. Сохранить работу и объединить исходники

Все Git-команды выполняются из `D:\CAD-Automation\team\Projects`.
Перед переключением веток или обновлением:

```powershell
Set-Location 'D:\CAD-Automation\team\Projects'
git status --short --branch
```

Если есть изменённые или новые файлы — сначала закончить/сохранить свои изменения
коммитом. Чужие правки не удалять. При непонятном составе показать status агенту;
не применять вслепую reset/clean/stash. Если Git сообщает о незавершённом merge,
сначала закончить или отдельно разобрать именно его.

Для своих готовых правок в **andrew** просмотреть `git diff`, получить у агента
точный список файлов для `git add`, добавить только согласованные файлы, затем:

```powershell
git diff --cached --stat
git commit -m "fix: describe the change"
git push -u origin andrew
```

`--cached` показывает подготовленные к коммиту изменения, `--stat` — сводку по
файлам; `-m` задаёт сообщение коммита (заменить осмысленным); `-u` запоминает
удалённую ветку для следующих push/pull. Открыть PR **andrew → develop**,
проверить **base: develop, compare: andrew**, выполнить проверку и merge на GitHub.
Агент готовит код и проверяет; Git-команды/merge делает пользователь.
У Артёма такая же схема с `artem`.

После принятия правок и при чистой папке получить общую версию:

```powershell
git fetch --prune origin
git switch develop
git pull --ff-only origin develop
```

`fetch` получает сведения с GitHub; `--prune` убирает ссылки на ветки, уже удалённые
на GitHub, а не локальные ветки или файлы. `origin` — имя GitHub-подключения.
`switch` выбирает ветку; `pull --ff-only` обновляет её только прямым продвижением,
без неожиданного merge-коммита. Если ff-only отказал — остановиться и показать
вывод, не добавлять force. Перед сборкой `git status --short --branch` должен
показать чистую develop без отставания от origin/develop.

### 2.2. Собрать один новый выпуск и положить на NAS

Готовый ZIP собирается **один раз ответственным**, из принятой чистой develop.
На машине сборки требуются .NET 10 SDK и установленный AutoCAD 2027; для
плагина 2026 используются compile-only ссылки AutoCAD.NET **25.1.0**, не 25.1.1.
Python требуется только дополнительным диагностическим скриптам, не пользователям ZIP.

Попросить агент проверить состав изменений и выполнить соразмерные проверки.
Полный offline-набор, если он требуется изменениями кода:

```powershell
Set-Location 'D:\CAD-Automation\team\Projects\cad-bridge'
dotnet test .\upstream\dwg-mcp\tests\Bimwright.Dwg.Tests\Bimwright.Dwg.Tests.csproj -c Release
```

`-c Release` выбирает конфигурацию сборки. При изменении общего кода собираются
оба плагина; проверка схем выполняется через реальный MCP SDK без CAD-вызовов.
Упаковщик собирает плагины и самодостаточный сервер; новые команды с известным
результатом не нужно многократно повторять. Для одних инструкций сборка не нужна.

После проверок выбрать **новый свободный номер**, например `2.0.1-team.4`:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\package-team-dwg.ps1 -Version 2.0.1-team.4
```

`-Version` — номер создаваемого выпуска; в примере он не означает, что такой
стабильный выпуск уже существует. Результат находится только в
`cad-bridge/releases/team/2.0.1-team.4/`: ZIP и соседний `.sha256`.
Проверить manifest, хеши и запуск EXE/MCP, установить локально по пункту 2.3
и выполнить согласованную нативную проверку. После успешного пилота скопировать
эти **два файла** в новую папку версии на NAS. Готовый архив не переименовывать
в другую версию и не перезаписывать старый выпуск.

До коммита допускается только отдельный тестовый RC с явным `-AllowDirty`:
флаг разрешает незакоммиченные исходники, manifest фиксирует `dirty=true`.
Такой RC не выдаётся за стабильный командный выпуск. Окончательный пакет
собирается после принятия кода. Успешный offline-прогон не заменяет проверку
автозагрузки AutoCAD/Civil 3D на нужной машине.

### 2.3. Обновить установленный мост

Выполнить пункты **1.4 и 1.6**: нужный ZIP + SHA → распаковка → закрыть CAD и
Codex → `install.ps1 -Years 2027 -Client none` → обычный запуск → чтение MCP.
Для уже подключённой машины по прежнему пути `server/current` повторять
`setup-codex.ps1` обычно не требуется. Он нужен при первой настройке, смене
года или пути подключения.

После работы с выпуском вернуться к собственной ветке. Из чистой папки Projects:

```powershell
Set-Location 'D:\CAD-Automation\team\Projects'
git switch andrew
git pull --ff-only origin andrew
git merge develop
```

`merge develop` включает принятый командный код в личную ветку. При конфликте
не продолжать работу наугад: разрешить конфликт и проверить объединение вместе
с агентом. Если понадобился новый merge-коммит, опубликовать его обычным push.
Исходники, установленные DLL и папки чертежей при этом остаются разными вещами.

## 3. Обновление других уже подключённых машин

На каждом компьютере сотрудника:

1. Получить **назначенную версию ZIP и её `.sha256`** с NAS. Если сотрудник
   только пользуется инструментом, делать Git pull и собирать сервер ему не нужно.
2. Выполнить **пункт 1.4**: проверить SHA, распаковать локально, сохранить работу,
   закрыть AutoCAD/Civil 3D и Codex, запустить установщик для своего года.
3. При прежнем подключении `server/current` оставить его настройки; `setup-codex`
   повторяется только при первой настройке/изменении года или пути.
4. Выполнить **пункт 1.6**: обычный запуск без NETLOAD → документ → Codex →
   чтение сведений. Сообщить ответственному версию пакета, год/продукт и результат.
5. Если сотрудник развивает мост, отдельно обновить его исходники по общей Git-схеме
   и включить develop в его личную ветку. Это не заменяет установку из шага 2.

Обновление одного компьютера не меняет запущенный мост остальных. Каждый
обновляет свою установку между сеансами; автоматического обновления с NAS пока нет.
Выключенные старые bundle вручную возвращать не нужно: установщик ставит новый
пакет на штатное место. Сторонние плагины не перемещать при обычном обновлении.

## Где смотреть версию и что делать при сбое

Стандартные пути на каждой машине:

| Файл/папка | Назначение |
| --- | --- |
| `%APPDATA%\Autodesk\ApplicationPlugins\Bimwright.Dwg.bundle` | Установленный native-плагин |
| `%LOCALAPPDATA%\Bimwright\Dwg\server\current\dwg-mcp.exe` | Сервер, запускаемый Codex |
| `server/current/bridge-docs/AGENTS.md` | Правила работы установленного моста |
| `server/current/bridge-docs/release.json` | Точная версия установленного командного пакета |
| `%LOCALAPPDATA%\Bimwright\Dwg\debug.log` | Ошибки запуска и обработчиков со стеком |

Напечатать версию и последние записи журнала можно так:

```powershell
Get-Content -LiteralPath "$env:LOCALAPPDATA\Bimwright\Dwg\server\current\bridge-docs\release.json"
Get-Content -LiteralPath "$env:LOCALAPPDATA\Bimwright\Dwg\debug.log" -Tail 40
```

`-Tail 40` показывает последние 40 строк. В журнале важны время и стек именно
проблемного запуска. При отсутствии связи сначала проверить наличие документа,
нужный год подключения и сообщения AutoCAD; `MCPSTART` позволяет повторить старт.
`MCPSTOP` до первого документа отменяет ожидающий автоматический запуск.
При повторном фатальном сбое передать журнал и версию ответственному;
не сбрасывать профиль и не переустанавливать AutoCAD наугад.

## LISP и правила развития

Пользовательские `.lsp` **не входят** в установочный ZIP. Их передают отдельно
из согласованной библиотеки. Для запуска через MCP пользователь разрешает
конкретный локальный файл/функцию командой `MCPTRUSTLISP`; изменение файла требует
нового доверия. Полная процедура — в [CAD_WORKFLOW.md](CAD_WORKFLOW.md#запуск-autolisp).

Правила моста — [AGENTS.md](../AGENTS.md), технический процесс доработок —
[CAD_WORKFLOW.md](CAD_WORKFLOW.md), один журнал — [WORK_STATUS.md](../WORK_STATUS.md).
Ссылки на корневой AGENTS и WORK_STATUS относятся к исходникам Git. В установленной
папке bridge-docs правила AGENTS.md лежат рядом с этой памяткой; журнал туда не
копируется и читается в репозитории. Второй журнал в установке создавать не нужно.
История первоначального импорта — [IMPORT_MANIFEST.json](IMPORT_MANIFEST.json);
патчи из `patches/` уже применены. Сборки, ZIP и локальные Python-окружения
не коммитятся. У каждого разработчика своя папка Projects; один checkout не
редактируется несколькими чатами одновременно без согласования.
