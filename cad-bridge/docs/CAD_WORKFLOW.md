# Развитие общего CAD-моста

Одна локальная установка обслуживает все проекты чертежей на компьютере.
Исходники находятся в этом проекте `cad-bridge`, реализация — `upstream/dwg-mcp`.
У каждого разработчика свой checkout Projects. Сборки устанавливаются локально;
через Яндекс Диск передаются версии ZIP, а изменения кода — через Git.

Канонические правила — в `cad-bridge/AGENTS.md`, состояние — в
`cad-bridge/WORK_STATUS.md`. На этом компьютере source root:
`D:\CAD-Automation\team\Projects\cad-bridge`. Действующий runtime AutoCAD 2027
остаётся в `D:\CAD-Automation\releases\dwg-2027\2026-10-06-style-tools`;
его установка и подключение не меняются от очистки исходников.

## Когда добавлять инструмент

1. Проверить существующие typed-инструменты и фактическую MCP-схему.
2. Если операция общая для чертежей (вес, заливка, свойства, геометрия), добавить
   её в мост. Состав таблицы, имена слоёв и размещение символов — задача проекта.
3. Изучить upstream и официальные Autodesk API/примеры. Определить параметры,
   единицы, ограничения и ошибки. Небольшую доработку выполнять в разрешённых
   рамках; крупную незавершённую — записать в WORK_STATUS.md с следующим шагом.
4. C#-сценарий допустим как прототип нативной операции. Успех сценария не означает
   готовность typed-инструмента и не оправдывает повторение одного обходного пути.

## Как проходит изменение

- При совместной разработке пользователь создаёт рабочую ветку от актуальной
  `develop`, затем делает commit, push и pull request (PR) в `develop`.
  Агент готовит правки и помогает оценить diff; пользователь выполняет merge.
- Агент проверяет текущие изменения, добавляет метод MCP, схему, обработчик плагина,
  dispatch и валидацию. Общая реализация размещается в `src/shared` для обоих годов.
- Перед записью проверяются документ/объекты/слои; используется транзакция.
  Ограничения Undo и частичного успеха обозначаются явно.
- Агент собирает и проверяет offline-контракт, включая реальные MCP-схемы.
  Пользователь выполняет загрузку DLL и явно включённые live-проверки; тест
  удаляет только свои объекты и не сохраняет DWG. Не повторять неопределённые мутации.
- После merge изменений поставляемого кода выпускается новый ZIP. Каждый участник
  устанавливает его локально при закрытых AutoCAD/Codex. Изменение плагина требует
  новой сессии AutoCAD, изменение только сервера — обновления MCP-подключения.
  Коммит не обновляет DLL. Для правок только документации достаточно просмотра
  diff; повторять сборки и успешные тесты или заменять рабочий ZIP не требуется.
- В WORK_STATUS.md отдельно записываются исходники, offline, загруженная версия,
  live-результат и следующий шаг. Не объявлять все инструменты проверенными по tools/list.

Первоначальные `patches/` уже применены в импортированных исходниках. Дальнейшие
изменения фиксируются обычными коммитами Projects. Upstream-база и хеши импорта —
в IMPORT_MANIFEST.json; обновлять upstream следует отдельной проверяемой задачей.

## Совместные правки

Checkout — обычная локальная папка с файлами репозитория и скрытой папкой `.git`.
У автора и ГИПа свои папки на своих компьютерах; GitHub хранит общую историю.
Ветка выбирает версию файлов в этой папке. Коммиты фиксируют изменения, рабочая
ветка позволяет подготовить их до включения в общую `develop`.

1. До начала реализации согласовать задачу, исполнителя и пересекающиеся файлы.
   Общая очередь находится в WORK_STATUS.md. Запись задачи не означает начало
   реализации; новые запросы ГИПа сначала добавляются с ожидаемым результатом.
2. Пользователь обновляет локальную `develop` из GitHub и создаёт свою рабочую
   ветку: `feat/...` для инструмента, `fix/...` для исправления, `docs/...` для
   документации. При параллельной работе изменения идут через PR в `develop`.
3. Агент перед записью проверяет текущий diff. Чужие незакоммиченные правки
   сохраняются и явно учитываются в составе будущего коммита. Если другой чат
   редактирует те же файлы в той же папке, сначала согласовать передачу работы;
   переключение ветки в общей папке затронет оба чата.
4. Разные ветки не исключают конфликтов. Изменения общих методов и разделов
   журнала согласовываются; при пересечении один участник ждёт принятия другого.
   Две сессии не выполняют одновременно изменения одного чертежа AutoCAD.
5. Перед коммитом просмотреть diff и добавить только согласованные файлы.
   Пользователь публикует рабочую ветку и открывает PR в `develop`; коллега
   проверяет состав и ограничения. Merge выполняет пользователь.
6. Если `develop` изменилась, пользователь сначала включает её изменения в
   рабочую ветку обычным merge, разрешает конфликты и проверяет объединённый diff.
   Для кода повторяются затронутые проверки. История опубликованной совместной
   ветки не переписывается; принудительный push не используется.

Новые инструменты сначала проходят проверку исходников и offline-контракта.
Загрузка плагина и live-проверки выполняются отдельно по правилам AGENTS.md.

## Работа из других чатов

Установщик добавляет в личные инструкции Codex указатель на установленные правила.
При новых сборках это точная копия канонического `cad-bridge/AGENTS.md`;
отдельного редактируемого файла правил runtime в исходниках нет.
Для разработчика `-BridgeSourceRoot` указывает на его локальный каталог `cad-bridge`,
содержащий AGENTS.md, WORK_STATUS.md и этот файл. История другого чата не переносится:
общие решения и ограничения читаются из этих файлов. Правила конкретного чертежа
остаются в его AGENTS.md; сервер к каждому проекту копировать не требуется.

Для готового runtime checkout не нужен. Если задача требует развития моста,
а исходники недоступны, сначала сообщить о недостающем checkout и контракте
операции; не создавать параллельный сервер или новую папку документации.

Не вести одновременно конфликтующие изменения общей реализации и записи в одну
сессию AutoCAD. Проверять чужие изменения до правок и сохранять их. Передача
сообщений другим чатам требует прямого поручения пользователя.
