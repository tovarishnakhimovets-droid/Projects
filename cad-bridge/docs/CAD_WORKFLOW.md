# Устройство и доработка CAD-моста

Правила для чатов — AGENTS.md в корне исходников или рядом в runtime; подключение/Git/выпуск —
[TEAM_SETUP.md](TEAM_SETUP.md), контракты инструментов — [TOOLS.md](TOOLS.md),
проверенные результаты и очередь — WORK_STATUS.md в исходниках. Здесь ведётся
только техническая инструкция, без повторения памятки и журнала.

## Устройство

MCP-клиент запускает локальный сервер .NET 8 и общается по stdio; stdout занят
только MCP-протоколом. Сервер не ссылается на Autodesk DLL. В AutoCAD загружен
плагин соответствующего года: 2026 / .NET 8 или 2027 / .NET 10. Между ними —
локальный named pipe с JSON-запросами и токеном текущей сессии.

Плагин пишет discovery в `%LOCALAPPDATA%\Bimwright\Dwg\acad-YYYY.json`: год,
PID, transport, pipe_name, auth_token и время запуска. После перезапуска слушателя
токен меняется; сервер читает актуальную регистрацию и проверяет живой PID.
Target задаётся четырёхзначным годом. Таймаут связи — 30 секунд; он не прерывает
зависший native-вызов и не доказывает откат записи.

Для последовательного чтения нескольких открытых DWG использовать
`dwg_list_documents` → `dwg_use_document`: цель хранится в отдельном stdio-процессе,
вкладка пользователя не переключается. Ограничения неактивного DWG, срок действия
ID и возврат к активной вкладке — [TOOLS.md#documents](TOOLS.md#documents).

Внутренние команды явно регистрируются в `CommandDispatcher`, MCP-методы —
отдельно с префиксом `dwg_`. Общий код — `dwg-mcp/src/shared`, обработчики —
`shared/Handlers`, MCP-обёртки — `src/server/Tools` внутри `dwg-mcp`.
`DocumentInvoker`/`MainThreadExecutor` передают CAD-работу на основной поток:
lock/transaction не разрешают вызовы Autodesk API в фоновом потоке.
C#-прототипы синхронны; async/await и загрузка внешнего исходника не поддержаны.
Это полный доступ процесса, а не песочница. Штатный командный профиль не требует
включения C# или ToolBaker.

Настройки профиля приложения отделены от объектов DWG. Контракты общего
каталога, чтения/изменения и перекрестия находятся в
[TOOLS.md#settings](TOOLS.md#settings) и
[TOOLS.md#crosshair-settings](TOOLS.md#crosshair-settings).

Слова пользователя «выбранные/выделенные объекты» означают текущее pickfirst-
выделение: сначала `dwg_get_selection`, затем нужные свойства по его handles.
Пустой выбор не заменять поиском; неполный ответ не считать полным составом.
Контракт и ограничения — [TOOLS.md#selection](TOOLS.md#selection).
Для простой прямой MLeader использовать существующий `dwg_create_leader` из
`drawing`; отдельный LISP или сценарий создания такой выноски не нужен.

## Выбор способа доработки

Перед написанием кода выбрать, что требуется: порядок работы существующими
инструментами, новая операция MCP или самостоятельная команда AutoLISP.
Общность задачи, частота использования, сложность и число строк сами по себе
не определяют выбор. MCP может запускать LISP через существующий dwg_run_lisp;
это ещё не требует нового MCP-инструмента для каждой команды.

| Потребность | Где реализовать | Примеры |
| --- | --- | --- |
| Правила выбора объектов, оформления или подсчёта; имеющихся средств чтения/записи достаточно | Инструкция или навык поверх существующих инструментов | Подсчёт ФБС по рамкам профиля, правила слоёв и условных обозначений. |
| Операция как часть поддерживаемого API моста: существующие средства не дают требуемых параметров, лимитов, проверок или результата | Типизированный инструмент MCP в .NET-мосте | Чтение атрибутов, вес линии, SOLID-заливка, настройки приложения; проверяемое разбиение сети по узлам. |
| Законченная прикладная команда AutoCAD, которую сотрудник запускает и при необходимости отвечает на её запросы | Общий LISP в lisp/ | NETLEN, PLLEN, PLLENLEADERS; повторяемое оформление по принятому шаблону. |
| Одноразовое исправление с путями, handles или координатами конкретного чертежа | Сценарий проекта вне общей библиотеки | Сохранённый sandbox.lsp для конкретной сети. |

**Порядок решения:**

1. Прочитать фактический tools/list и найти существующую команду/реализацию.
   Использовать готовые средства; повторяемый порядок и инженерные правила
   записать в инструкцию. Дублирующий код для этого не нужен.
2. Если не хватает операции с CAD-объектами, сформулировать её входы, единицы,
   границы, проверки и результат. Добавлять MCP-инструмент с явными типами
   и лимитами, когда нужен самостоятельный контракт моста, а готовые инструменты
   и разрешённый запуск LISP не обеспечивают конкретные требования к доступу,
   проверкам или результату. Сам вызов операции моделью не требует нового
   .NET-инструмента. Несколько связанных изменений могут составлять одну
   операцию, если нужны общие проверки и транзакция.
3. Если нужна команда, которая за один запуск решает прикладную задачу
   сотрудника, использовать LISP. Повторное применение в других проектах
   делает его общим LISP, без обязательного переноса в .NET. Для подходящей
   команды допустим запуск через dwg_run_lisp по правилам ниже.
4. Если подходят оба варианта, выбрать меньшую доработку, которая выполняет
   требования к вводу, результату и проверкам. Кратко объяснить выбор перед
   реализацией. Сохранять одну реализацию операции.

**Когда пересмотреть готовый LISP:** выявлено конкретное ограничение текущей
команды и способа запуска. Например, регулярной программной обработке мешает
ручной ввод или разбор вывода, невозможно обеспечить нужные проверки,
объём или скорость. Сначала описать ограничение и требуемый контракт, затем
выбрать доработку LISP или операцию MCP. Само желание устойчивой схемы,
более редкой пересборки сервера или отсутствия подтверждения доверия
не требует переноса команды и не отменяет ограничений запуска.

LISP может принимать данные, возвращать результат и иметь свою группу Undo;
MCP сам по себе не гарантирует транзакцию или откат. Это проверяется для
конкретной реализации. При переносе выделить общую операцию и обновить вызовы;
не оставлять две независимо изменяемые реализации. Прикладная LISP-команда
может остаться, если её работа отличается от добавленной базовой операции.
Не добавлять произвольный eval/inline-исполнитель и не обходить ограничения
LISP через C#, batch или ToolBaker. Незавершённый прототип записать в очередь
WORK_STATUS с ограничениями; не выдавать его за готовый типизированный инструмент.

Это правило команды, основанное на способах использования:
[MCP tools описывают параметры и результаты вызова](https://modelcontextprotocol.io/specification/2025-06-18/server/tools),
а [AutoLISP позволяет определять команды AutoCAD](https://help.autodesk.com/cloudhelp/2027/ENU/AutoCAD-AutoLISP/files/GUID-EF910176-86D2-4158-A7C3-E926A002F421.htm).

## Технический цикл доработки

1. До первых правок выполнить обновление по AGENTS: проверить личную ветку,
   upstream/worktrees и чистоту; сначала fast-forward личной и локальной develop.
   При расхождении агент изучает историю и выполняет обычное слияние, если
   результат однозначен. Незавершённую свою доработку продолжать без нового pull.
   Затем перечитать правила, текущий diff и очередь; согласовать пересекающиеся
   файлы с коллегой. Порядок Git-работы агента — в TEAM_SETUP.
2. Проверить фактический tools/list и существующие реализации. Выбрать MCP,
   LISP или инструкцию по разделу «Выбор способа доработки». Указанные дальше
   действия с MCP-методом/schema/handler относятся к изменению самого моста;
   для LISP действует раздел «Создание и обновление AutoLISP».
3. Изучить upstream и официальные Autodesk API/примеры. Задать типы, единицы,
   лимиты, проверки, ошибки и поведение при частичном результате/Undo.
4. Добавить MCP-метод, schema, handler, dispatch и валидацию. Чистую логику
   отделить от Autodesk API. Перед записью — preflight и транзакция.
5. Проверить затронутую логику, реальные MCP SDK-схемы и read-only отказы.
   При общем коде собрать **оба** плагина. Native UI выполняет пользователь;
   offline PASS не разрешает live-тест и не подтверждает Undo или поведение DWG.
6. Обновить TOOLS, если изменился контракт, и один WORK_STATUS: source/offline,
   установленная/загруженная версия, live-результат, ограничения и следующий шаг.
   Затем агент выполняет commit/push/PR/merge по памятке без повторных запросов
   разрешения на Git. При неясном конфликте или недоступном входе сообщает
   конкретную проблему; обычные Git-операции пользователю не передаёт.

Полный offline-набор при необходимости, из `cad-bridge`:

```powershell
dotnet test .\dwg-mcp\tests\Bimwright.Dwg.Tests\Bimwright.Dwg.Tests.csproj -c Release
```

`-c Release` выбирает конфигурацию сборки. Для 2027 нужны .NET 10 SDK и DLL
установленного AutoCAD 2027; для 2026 — .NET 8 и compile-only AutoCAD.NET 25.1.0
с `UseAutoCadNuGetRefs=true`. Не заменять на 25.1.1: она рассчитана на .NET 10.
Диагностика MCP и live-параметры — [TOOLS.md#checks](TOOLS.md#checks).
Установщик собирается после принятия кода из чистой develop по TEAM_SETUP;
для документационных правок пересборка не требуется.

Старые plugin-acad22…25 сохранены как часть импортированного проекта;
`plugin-acad24/App.cs` общий и для 2026/2027. Не удалять его по имени версии.
Сборка 2024 использует локальные AcMgd/AcCoreMgd/AcDbMgd из AutoCAD 2024,
при необходимости путь задаёт MSBuild-свойство `AutoCad2024Dir`; Autodesk DLL
в Git и поставку не входят. Текущий командный установщик поддерживает 2026/2027.

Происхождение — [IMPORT_MANIFEST.json](IMPORT_MANIFEST.json): это исторический
снимок импорта, а не текущий список файлов. Патчи из `patches/` уже применены;
дальнейшие правки идут обычными коммитами. Их не применять повторно.

## Перевод и оформление текста

Прикладной перевод выполняется этим сценарием поверх обычных CAD-инструментов.
`dwg_translate_and_rewrite` и `dwg_apply_unicode_style` удалены из нового моста;
их старые варианты в установленной версии не означают, что исходники не обновлены.
У `update_texts` и `collapse_and_rewrite` больше нет автоматического Unicode,
создания фирменного слоя или скрытого уменьшения высоты. Старые параметры
`apply_unicode_style`/`final_scale` отклоняются; обновить сценарий, не повторять вызов.

1. Прочитать текущий чертёж, определить состав через `dwg_get_selection`, затем
   извлечь текст через `dwg_get_selected_texts(includeEntities=true)`.
   Выделение задаёт пользователь; не заменять пустой pickfirst всем чертежом.
   Группы — подсказка чтения, а не сохранённый план записи. Их ID действуют
   только в этом ответе. Для действий использовать свежие handles, тексты,
   owner и геометрию `entities`; исходный текст/единицы/обозначения сохранить
   в плане. Bounds с `bounds_available=false` не считать измеренной рамкой.
2. Подготовить перевод. Числа, отметки и технические обозначения без перевода
   сохранять. Направление чтения, объединение строк и переносы выбирать по
   фактическому расположению; одна пространственная группа ещё не разрешает
   сливать разные подписи. Для многострочного MText использовать `\P`
   (в JSON-строке обратный слеш экранируется: `\\P`).
3. Обычную замену, в том числе текста MLeader/AttributeReference, выполнять
   `dwg_update_texts`. Она сохраняет оформление и геометрию. Когда действительно
   нужно объединить фрагменты DBText/MText или преобразовать текст в MText,
   использовать `dwg_collapse_and_rewrite`: точные anchor/delete handles,
   новый текст и явные размеры. Контракт — в TOOLS. Каждый элемент имеет свою
   транзакцию; не считать весь запрос одной отменой или общим откатом.
4. Размеры переписывания задаются в координатах владельца объекта. Для обычного
   пространства это единицы чертежа; внутри определения блока — его локальные
   единицы. `height`/`bounds` чтения находятся в WCS, `local_height` и
   `local_position` — в локальной системе. Не делить на `block_scale` размеры,
   уже взятые из local-полей; одного масштаба недостаточно для повёрнутой или
   неравномерно масштабированной рамки. Изменение определения блока затрагивает
   все его ссылки: до такой правки проверить и объяснить охват. По умолчанию
   высоту сохранять, ширину/переносы менять по задаче и визуальному результату,
   без прежнего неявного множителя 0.80.
5. Если требуется фирменное Unicode-оформление, использовать единственную
   реализацию `lisp/apply_unicode_style.lsp`: команда `BWUNICODE` для пользователя
   или функция `bw:apply-unicode` с точными handles и путём TTF. После merge
   брать **new_handle** из успешного результата; старый anchor может быть стёрт.
   Непереводимые числа включать в оформление только в пределах запрошенного
   набора. LISP получает отдельный допуск MCPTRUSTLISP и запускается по разделу
   «Запуск AutoLISP»; сам сценарий не обходит доверие и не разрешает сохранение.
6. Перечитать тексты и проверить вид. При частичном отказе учитывать успешные
   элементы и новые handles; при неизвестном исходе записи сначала читать
   состояние. Текстовая правка и последующее LISP-оформление — разные действия,
   их общий Undo/откат не обещается.

Шрифт хранится единственным файлом `lisp/OpenSans-CondensedLight.ttf` рядом с
командой. В аргументе передавать полный путь своей локальной копии, например
`D:\CAD-Automation\team\Projects\cad-bridge\lisp\OpenSans-CondensedLight.ttf`.
Перед первым `BWUNICODE` установить этот TrueType-шрифт в Windows и перезапустить
AutoCAD: одного TTF рядом с LISP недостаточно. Файл можно открыть в Windows и
нажать «Установить»; LISP не устанавливает и не скачивает шрифты. Это требование
[Autodesk к TrueType-шрифтам](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/Where-to-install-font-shape-files-in-AutoCAD.html).
Происхождение и лицензия —
`dwg-mcp/THIRD_PARTY_NOTICES.md` и `lisp/OFL.txt`.

Программная функция принимает `arguments_json` вида
`[["1A2B","1A2C"],"D:/CAD-Automation/team/Projects/cad-bridge/lisp/OpenSans-CondensedLight.ttf"]`.
`completed` у LISP-job подтверждает выполнение функции, а результат
`bw:apply-unicode` отдельно содержит `ok`, `phase`, `partial_changes` и
`rollback_verified`. Проверить их в напечатанном alist; `ok=nil` — отказ,
даже если функция завершилась без исключения. Восстановление свойств после
ошибки относится к записанным объектам/ресурсам, а не ко всему DWG или Undo.
Оформление отказывает для полей, аннотативных объектов/стилей, inline-переопределений,
xref, неподдержанных блоков и закрытых/замороженных/заблокированных слоёв;
чужой несовместимый стиль или слой не перезаписываются. При отказе не упрощать
проверки автоматически; сначала разобрать конкретный объект.
У MLeader сохраняются базовая точка, точки соединения и вершины линий.
AutoCAD пересчитывает внутреннее положение MText по метрикам шрифта,
высоте и типу прикрепления; равенство всех DXF-координат текста не обещается.
Эти данные отделены от контрольных точек в
[Autodesk MLeader Context Data](https://help.autodesk.com/cloudhelp/2023/ENU/AutoCAD-DXF/files/GUID-EC56D0DE-026D-46AB-87B1-9692393B0C22.htm).
Явные handles текстов в обычном определении блока поддержаны: оформление,
как и переписывание, затронет все ссылки на это определение. Анонимные и
динамические определения и вложенные block references отклоняются. Перед
вызовом объяснить этот охват; не выдавать правку определения за правку экземпляра.
Через MCP передавать небольшие пачки, например до 90 handles: `arguments_json`
ограничен 100 узлами. Подробный отчёт содержит до 10 объектов и показатели
`object_count`/`objects_reported`/`objects_complete`; это не ограничивает
проверку остальных целей. Для деталей перечитать все запрошенные handles.

## Сетевые операции, proxy и SaveAs

| Инструмент | Область операции |
| --- | --- |
| `dwg_inventory_proxies` | Ограниченный обход handles всей БД, включая определения блоков и неграфические proxy; классы, владельцы, разрешения, полнота результата. |
| `dwg_erase_proxy_objects` | 1–1000 явно выбранных неграфических ProxyObject; точные ожидания класса/DXF/application/owner, preflight и одна транзакция. |
| `dwg_node_network` | Split/snap заданных Line/open lightweight Polyline в заданных существующих узлах; первый фрагмент сохраняет исходный handle. |
| `dwg_move_network_endpoint` | Одна транзакция для конца open lightweight Polyline, соответствующего простого блока и всех его атрибутов. |

Перед новой записью прочитать `dwg_get_drawing_info` и передать `document_path`
как `expected_document`, `fingerprint` как `expected_fingerprint`. Оба поля
обязательны у трёх новых write-инструментов. Путь должен быть полным путём
именованного DWG; DWT и несохранённый чертёж не подходят. Новое чтение отдельно
возвращает `database_filename`, `original_filename`, `is_titled`, `file_exists`,
`file_read_only`, `document_read_only` и `dbmod`. Существование файла само по себе
не доказывает, что последние изменения сохранены.

Для сетевых операций вызвать `dwg_get_entity_properties` с нужными handles и
`includeGeometry=true`. Ответ содержит `document_path`/`fingerprint`, а для каждого
успешно прочитанного объекта — `type`, `layer`, `owner_handle` и геометрию:

- Line: `start`/`end`; Polyline: полный упорядоченный `vertices`, `normal`,
  `elevation`, `thickness`, `constant_width`, bulge/ширины каждой вершины.
- DBPoint и BlockReference: `position`; для блока также `name`, `normal`,
  `is_dynamic`, `attributes` и `attributes_complete`.
- Атрибут: `handle`, `tag`, `text`, `position`, `alignment_point`.
  Полный список обязателен; при `attributes_complete=false` правку не готовить.

Координаты чтения `{x,y,z}` передаются в параметры как `[x,y,z]`, без округления.
Ожидания берутся из свежего ответа: `expected_type/layer/owner_handle/vertices`
для sources; `expected_position` для nodes; геометрия, слои, имя блока и полный
список атрибутов для changes. Все координаты и допуски — WCS в единицах чертежа.
`dry_run=true` у write-инструментов выполняет проверки/план без записи и не
резервирует объекты: перед реальным вызовом ожидания проверяются снова.

Сетевые операции ограничены плоскими путями с нормалью +Z, прямыми сегментами,
нулевыми ширинами/thickness и общей высотой. Split/snap требует узел у обоих
концов каждого источника, режет во всех заданных внутренних узлах и отклоняет
неоднозначные узлы. Он не объединяет пути и не создаёт/перемещает узлы.
При разбиении связанные XData, dictionaries и persistent associations отклоняются.
Перемещение требует исходного точного совпадения endpoint и insertion; остальные
вершины и тексты атрибутов сохраняются. Dynamic/annotative/xref блоки, multiline/
annotative атрибуты и блокированные слои не поддерживаются. Число объектов,
вершин, сравнений и время ограничены; точные пределы видны в MCP-схеме/описании.

Proxy inventory по умолчанию ограничен 500000 попыток handles, 5000 мс и 1000
записей; ответ ограничен 2 МиБ. `complete=true` означает один полный проход от
начала без ошибок/лимитов со стабильным handseed. `range_complete` относится
только к суффиксу текущей страницы. Продолжение через `next_after_handle` требует
обоих identity-полей; страницы — независимые чтения, изменение handseed требует
новой инвентаризации. `metadata_complete=false` исключает запись по такой записи.
Текстовая классификация Civil/AEC/Map — подсказка, а не разрешение удаления.

Удаление допускает только ProxyObject с нативным erase permission, доступным
локальным владельцем, без ссылок `GetReferences` и непустого extension dictionary.
ProxyEntity, native объекты и неявное удаление dictionary/service roots запрещены.
Это консервативная часть очереди очистки; многие связанные Civil proxy будут
отклонены. Нативные reactors могут влиять на связанное состояние.
[Контракт GetReferences](https://help.autodesk.com/cloudhelp/2026/ENU/OARX-ManagedRefGuide/files/OARX-ManagedRefGuide-Autodesk_AutoCAD_DatabaseServices_ProxyObject_GetReferences.html).

`dwg_save_drawing` сохраняет прежние параметры и добавляет необязательную пару
`expected_document`/`expected_fingerprint`: если задано одно, требуется второе.
Preflight проверяет read-only состояние и совпадение пути с другим открытым DWG.
Для смены имени используется четырёхпараметрический `Database.SaveAs` с
`bBakAndRename=true`, затем проверяется новый путь документа.
[Документация Autodesk SaveAs](https://help.autodesk.com/cloudhelp/2026/ENU/OARX-ManagedRefGuide/files/OARX-ManagedRefGuide-Autodesk_AutoCAD_DatabaseServices_Database_SaveAs_string__MarshalAsUnmanagedType_U1__bool_DwgVersion_Autodesk_AutoCAD_DatabaseServices_SecurityParameters.html).
Это подготовленное исправление, а устранение eFilerError и поведение вкладки ещё
не проверены в AutoCAD. Любое сохранение требует запроса пользователя.

Новые операции не сохраняют DWG автоматически и не обещают grouped Undo.
После таймаута записи не повторять вызов автоматически; сначала выяснить состояние.

## Создание и обновление AutoLISP

Общие команды хранятся в `cad-bridge/lisp/` этого репозитория. На командных
машинах полный путь — `D:\CAD-Automation\team\Projects\cad-bridge\lisp`.
Каждый редактирует и запускает свою локальную копию. NAS используется для
установщиков; отдельная раздача LISP и копии в установленном сервере не нужны.
В установленной bridge-docs этот путь также относится к исходникам Git.

| Файл | Команда AutoCAD | Назначение |
| --- | --- | --- |
| `netlen.lsp` | `NETLEN` | Суммы длин из выносок по типу трубы, футляру и способу прокладки; вывод в командную строку. |
| `polyline_lengths.lsp` | `PLLEN` | Создание текстовых подписей длины каждого сегмента выбранной полилинии. |
| `polyline_lengths_to_leaders.lsp` | `PLLENLEADERS` | Запись длины сегмента после `L=` в существующей выноске, найденной по стрелке; также есть команда `ДЛИНЫВЫНОСОК`. |
| `apply_unicode_style.lsp` | `BWUNICODE` / `bw:apply-unicode` | Фирменное Unicode-оформление выбранных или явно переданных текстов; сценарий выше. |

1. Перед правками обновить личную ветку по AGENTS и прочитать существующий файл.
   Изменять его на месте; новую самостоятельную команду добавлять в эту же папку.
   Не вести варианты `final/new/v2` рядом и не затирать доработки другого чата.
2. В начале файла описать команду, входные данные, единицы и изменения чертежа.
   Использовать именованную `c:`-функцию и уникальный префикс вспомогательных функций.
   Загрузка файла не должна автоматически менять чертёж или запускать команду.
   Проектные пути, handles и координаты относятся к конкретному проекту;
   общая команда получает их от пользователя или текущего выбора.
3. Проверить синтаксис и формат файла по требованиям ниже. Проверку в AutoCAD
   проводить только по явному разрешению пользователя; не сохранять DWG без запроса.
   Записать фактический результат и ограничения в общий WORK_STATUS.md.
4. Commit/push/PR/merge — по TEAM_SETUP. После принятия остальные получают
   LISP обычным обновлением репозитория. Сервер и установщик для изменения `.lsp`
   не пересобираются. Порядок запуска через MCP приведён ниже.

Локальный `D:\CAD-Automation\lisp\sandbox.lsp` — сохранённый сценарий конкретного
чертежа, вне общей библиотеки и Git; не использовать как пример общей команды
или проверку связи. При переносе либо изменении общего файла требуется новый
допуск MCPTRUSTLISP для его фактического пути, байтов и функции.

## Запуск AutoLISP

Для запуска нужны `dwg_run_lisp` и `dwg_get_lisp_status` в подключённом сервере
и соответствующая DLL. Старые team.2/style-tools отказывают в запуске LISP.
Доступность и нативные результаты проверяются отдельно; состояние — в WORK_STATUS.md.

1. В новой сессии AutoCAD загрузить новый плагин. Обновить подключение MCP на новый
   сервер. Пользователь разрешает конкретную live-проверку отдельно.
2. В AutoCAD выполнить `MCPTRUSTLISP`, выбрать локальный `.lsp`, указать функцию
   (`c:NETLEN`, `c:PLLENLEADERS` и т.п.), проверить показанные путь/SHA256/функцию
   и ответить `Yes`. По умолчанию ответ `No`. Доверие действует в этой сессии;
   изменение байтов файла требует нового допуска. Один файл может иметь несколько
   отдельно разрешённых функций. Статический `dwg_inspect_lisp` доверие не выдаёт.
3. Агент читает `dwg_get_lisp_status` для разрешённой версии и свежее
   `dwg_get_drawing_info` для `document_path`/`fingerprint`. У запуска обязательны
   `file`, `command`, `expected_sha256`, `expected_document`, `expected_fingerprint`.
   Нужен именованный DWG и свободная командная строка. Сам факт отказа для
   несохранённого чертежа не разрешает агенту сохранять его.
4. `dwg_run_lisp` возвращает `job_id` и `queued`. Агент опрашивает
   `dwg_get_lisp_status` с этим ID: `running` ещё не результат, `completed` —
   успешное завершение, `failed` — отказ/ошибка/отмена. Если скрипт запросил выбор
   объектов или ввод, пользователь отвечает в AutoCAD. Пока задача активна,
   остальные CAD-инструменты отказывают; статус доступен без ожидания ввода.
5. Ошибка после начала может оставить изменения. Проверить `execution_started`,
   `completion_confirmed`, `may_have_partial_changes` и фактический чертёж.
   Таймаут и ошибку не повторять автоматически. Для отмены работающего скрипта
   пользователь использует AutoCAD; MCP не обещает откат.

Допускаются самостоятельные файлы до 64 КиБ: UTF-8 с BOM или без него, UTF-16 с
BOM; `LISPSYS` должен быть 1 или 2. Мост читает байты один раз, проверяет SHA256 и
выполняет этот снимок исходника. Это не обычный `(load "file.lsp")`: скрипты,
зависящие от `*load-truename*` или относительной загрузки файлов, не поддерживаются.
Файлы FAS/VLX не принимаются на вход. Верхнеуровневые выражения файла тоже выполняются.
Аргументы функции необязательны: `arguments_json` содержит JSON-массив данных
(например, `[10,"текст",[1,2]]`), не Lisp-выражение; по умолчанию `[]`.

Разрешённый LISP имеет полный доступ процесса AutoCAD, включая файлы и вызываемый
им код. Допуск не создаёт песочницу и не проверяет безопасность зависимостей.
`MCPDISABLELISP`, `MCPSTOP` и завершение сессии очищают допуски; ожидающие задачи
отменяются, уже работающая задача остаётся активной до реального окончания.
Ожидание запуска ограничено минутой, история — 16 задачами. Нет выполнения
inline-кода, LISP внутри batch/ToolBaker и обхода через C#; DWG не сохраняется
самим мостом, но доверенный скрипт может иметь собственное сохранение.

Очередь использует официальный асинхронный
[SendStringToExecute](https://help.autodesk.com/cloudhelp/2026/ENU/OARX-DevGuide-Managed/files/GUID-F4A36181-39FB-4923-A2AF-3333945DB289.htm),
обратный результат — [.NET LispFunction](https://help.autodesk.com/cloudhelp/2026/ENU/OARX-DevGuide-Managed/files/GUID-3B2760FE-A0DC-4229-AEBE-5CC83290BA95.htm).
Окончание подтверждается результатом и событиями LispEnded/LispCancelled;
принятие очереди и фиксированная задержка не доказывают выполнения.

## Работа из других чатов

Установщик добавляет в личные инструкции Codex указатель на установленные правила.
При новых сборках это точная копия канонического `cad-bridge/AGENTS.md`;
отдельного редактируемого файла правил runtime в исходниках нет.
Для разработчика `-BridgeSourceRoot` указывает на его локальный каталог `cad-bridge`,
содержащий AGENTS.md, WORK_STATUS.md и этот файл. История другого чата не переносится:
общие решения и ограничения читаются из этих файлов. Правила конкретного чертежа
остаются в его AGENTS.md; сервер к каждому проекту копировать не требуется.

Для готового runtime checkout не нужен. Если задача требует развития моста,
а исходники недоступны, сначала сообщить о недостающем checkout и контракте
операции; не создавать параллельный сервер или новую папку документации.

Не вести одновременно конфликтующие изменения общей реализации и записи в одну
сессию AutoCAD. Проверять чужие изменения до правок и сохранять их. Передача
сообщений другим чатам требует прямого поручения пользователя.
